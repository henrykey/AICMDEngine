# 云端构建与部署正式方案（AIPlanner）

## 1. 文档目的

本方案用于统一 AIPlanner 在云端（以阿里云 ECS 为例）的构建与部署流程，确保：

- 支持全量部署与分别部署
- 在指定 `--mirror cn` 时，所有依赖安装环节必须使用国内镜像源
- 部署结束后清理云端源码（成功和失败都清理）
- 区分“部署范围”和“默认自动启动范围”
- 避免因流程偏差导致 UI 启动失败、构建慢、构建不稳定

---

## 2. 适用范围

适用于以下服务：

- mcp-router
- plan2-ui
- office-word
- pdf2md-enhanced
- pageindex

说明：以上服务均为必要服务，不存在“永久不部署”的服务。只区分是否默认自动启动。

---

## 3. 核心原则（硬约束）

### 3.1 部署模式必须同时支持

- 全量部署：一次性构建并部署全部服务
- 分别部署：按服务组或单服务进行构建部署

### 3.2 `--mirror cn` 必须全链路生效

当使用 `--mirror cn` 时，以下环节必须全部命中国内镜像：

- apt install / apt-get
- apk add
- pip install
- npm install / npm ci（如涉及前端构建）
- 基础镜像拉取（如 node/python/nginx）

要求：

- 任一环节无法使用国内镜像时，必须在构建前或构建时明确报错并停止（fail-fast）
- 禁止静默回退到国外源

### 3.3 云端源码必须清理

- 每次部署使用临时源码目录（时间戳目录）
- 成功后清理
- 失败后也清理（通过退出钩子保证）
- 云端仅保留目标运行目录与必要配置文件，不保留源码副本

---

## 4. 为什么采用云端构建（本项目语境）

本项目采用云端构建的首要原因：

1. 上传更小、更快（网络慢条件下更关键）
2. 可直接使用云端国内镜像源（提高成功率）

注意：

- 若源码包体积过大，云端构建优势会下降甚至失效
- 若镜像源未全链路生效，构建会明显变慢或失败

因此，云端构建是否有效，取决于：

- 小源码包策略是否成立
- 镜像源策略是否无遗漏

---

## 5. 部署范围与启动范围设计

### 5.1 部署范围（Build + Deploy）

- `scope=all`：部署全部服务
- `scope=router`：仅部署 mcp-router
- `scope=plan2`：仅部署 plan2-ui
- `scope=mcp`：部署 MCP 子服务（office-word、pdf2md-enhanced、pageindex）
- `--services`：按服务名精确部署，支持单一服务或任意组合

服务名白名单：

- `mcp-router`
- `plan2`
- `office-word`
- `pdf2md-enhanced`
- `pageindex`

参数优先级：

- 同时传入 `--services` 与 `--scope` 时，`--services` 优先
- 未传 `--services` 时，按 `--scope` 语义执行

示例：

- 全量：`--scope all`
- 单一：`--services office-word`
- 组合：`--services mcp-router,plan2,pageindex,office-word`

### 5.2 默认自动启动范围（Auto Start）

默认自动启动建议：

- mcp-router
- plan2-ui

MCP 子服务：

- 可单独启动/重启
- 不强制绑定到默认自动启动链路

说明：

- “不默认自动启动”不等于“不部署”
- MCP 子服务仍属于全量部署对象

## 6. 镜像源策略（Mirror Policy）

### 6.1 统一参数语义

- `--mirror cn`：启用国内镜像策略
- 若未显式传 mirror，按默认策略执行

### 6.2 各链路镜像要求

- Debian/Ubuntu：必须替换 `deb.debian.org` / `security.debian.org`
- Alpine：必须替换默认 `dl-cdn.alpinelinux.org`
- Pip：必须使用国内 index-url（并设置 trusted-host）
- Npm：必须使用国内 registry
- Docker base image：必须命中镜像加速前缀或可达镜像仓库

### 6.3 失败策略

出现任意以下情况必须失败退出：

- 构建日志中出现国外源访问且未被允许
- 镜像参数未透传到某个 Dockerfile 构建环节
- 构建步骤检测到关键参数缺失

---

## 7. 包体积与效率策略

### 7.1 打包策略

- 按 scope 白名单打包
- 排除大目录与运行产物（如 node_modules、dist、缓存、测试输出）
- 禁止将依赖目录、镜像 tar、临时日志打入源码包

### 7.2 构建策略

- 所有依赖在云端安装（按镜像策略）
- 用 lock 文件约束版本（pip/npm）
- 利用 Docker 层缓存减少重复下载

### 7.3 效率目标

- 小包上传时间可控
- 镜像源命中稳定
- 构建失败可快速定位（日志中可见镜像源配置）

---

## 8. 源码清理策略

### 8.1 清理对象

- 远端上传包（例如 `aiplanner-source.tar.gz`）
- 远端临时解包目录（`/opt/*-src-时间戳`）

### 8.2 清理时机

- 部署成功：清理
- 部署失败：清理（trap/exit hook）

### 8.3 保留对象

- 目标运行目录（例如 `/opt/AICMDEngine`）
- compose/env/config 等必要运行配置
- 日志与数据目录（按运维策略）

---

## 9. 标准执行流程

1. 选择部署目标：`--services`（单一/组合）或 `--scope`（all/router/plan2/mcp）
2. 确认服务名合法且去重；若同时存在 `--services` 与 `--scope`，按 `--services` 生效
3. 指定镜像参数（如 `--mirror cn`）
4. 上传源码包与必要配置
5. 云端构建（全链路镜像源强制）
6. 按目标服务部署并启动
7. 健康检查
8. 清理云端源码与临时包

---

## 10. 验收清单（每次发布必过）

### 10.1 部署能力

- 可执行全量部署
- 可执行分别部署
- 可执行单一服务部署
- 可执行任意服务组合部署
- `--services` 与 `--scope` 同时存在时，优先级行为明确且可验证

### 10.2 镜像源能力

- `--mirror cn` 时，apt/apk/pip/npm 全部命中国内镜像
- 构建日志不出现未授权国外源

### 10.3 启动能力

- plan2-ui 启动成功且可访问
- mcp-router 启动成功
- MCP 子服务可单独启动并被 router 访问

### 10.4 清理能力

- 云端无残留源码目录（`*-src-*`）
- 仅保留运行目录与必要配置

---

## 11. 异常与回滚

### 11.1 构建异常

- 立即停止，不继续部署
- 输出具体失败环节（apt/apk/pip/npm/base image）

### 11.2 启动异常

- 保留现有运行容器不被破坏
- 仅回滚本次变更服务

### 11.3 网络异常

- 上传支持重试
- 重试失败后立即失败并提示，不做静默降级

---

## 12. 变更管理要求

- 未经确认，不得擅自修改部署策略
- 重大策略调整（部署范围、镜像策略、清理策略）必须先讨论后实施
- 任何优化必须不破坏本方案第 3 章硬约束

---

## 13. 当前结论（执行口径）

- 云端构建可以继续采用
- 但必须以“小源码包 + 全链路镜像强制 + 失败即停 + 源码清理”为前提
- 所有服务都要部署；只区分自动启动策略
